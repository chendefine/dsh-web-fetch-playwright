# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Challenge dead-end plain-HTTP fallback (`challengeHttpFallback`, default on).** When the browser cannot clear a Cloudflare challenge inside its whole window — the interactive checkbox was never offered, or verification refused it — the fetch now makes ONE plain-HTTP request for the same URL through the page's own request context: the same cookie jar (any clearance the profile holds rides along), the browser's own User-Agent, none of Chromium's render decisions. Many Cloudflare edges serve the real document to such a request while withholding the interactive challenge from the browser session itself — measured live on v2ex.com from a datacenter IP, where the browser drew an empty widget frame for 15s×2 and the plain request drew the full article. The fallback answer must itself be a non-challenge HTML document (checked at response level AND content level, through the same classifiers that gate the browser path); anything else — a challenge, a non-2xx, a non-HTML body, a transport failure — keeps the honest `WEB_FETCH_CHALLENGE` verdict, so the fallback can never smuggle an interstitial through as content.

## [0.2.21] - 2026-11-10

### Changed

- **The deep-capture scroll walk no longer waits ~4s on pages it cannot help.** If a page never adds or removes elements while being scrolled, and has made no fetch/XHR since the walk began, the walk now holds at the bottom for `SCROLL_INERT_PATIENCE_MS` (900ms) instead of `SCROLL_BOTTOM_PATIENCE_MS` (2.5s). Any reaction or data request, including one that arrives during the shorter hold, restores the full patience. Requests are counted with a `PerformanceObserver`. Polling the resource buffer would stop counting once Chromium's 250-entry buffer filled. A request is seen only when it completes, so a next chunk still loading when the short hold runs out is missed.
- **Discourse post timestamps (`pre` candidate) are now ISO calendar dates** (`2024-09-05`, UTC). They were previously US-English (`September 5, 2024`), whatever the language of the page or the reader.
- **Site-specific rules removed from the denoise features** (see `docs/benchmark-protocol.md`, rule 3):
  - The pinyin rail names `tuijian` / `xgtj` are no longer rail names. Rails are recognised by the generic `recommend*` / `related*` names and the Outbrain/Taboola widgets.
  - URL-shape features no longer match single-letter or store-specific path codes (`/p/`, `/c/`, `/t/`, `/dp/`, `/itm/`).
  - The Discourse generator signal no longer counts `.ember-application`, which every Ember app carries. It still counts `#data-preloaded[data-preloaded]` and `meta[name="discourse_theme_id"]`.
  - `consent_hits` now uses the same consent wording as the chrome stripper. A bare 同意 is no longer counted as consent wording, because it is ordinary prose.
- Both models were retrained on the changed features as the protocol requires: the block classifier first, then the selector on cross-fitted dumps. Stripped F1 compared with 0.2.20:

  | Dataset | 0.2.20 | Retrained |
  | --- | --- | --- |
  | WCXB dev | 0.8398 | 0.8377 |
  | WCXB test (held out) | 0.8691 | 0.8635 |
  | trafilatura | 0.8887 | 0.8881 |
  | ScrapingHub | 0.9397 | 0.9396 |

  First baseline on the sealed `fc` split (Firecrawl snapshot, 798 pages, CJK-aware word F1): 0.3135. Of that, CJK pages (60) score 0.3233 and the rest (738) 0.3127. Absolute scores include page drift since the truth text was written, so `fc` is meant only for comparing versions with each other.

  The largest per-type losses are on WCXB test collection (0.791 → 0.754), listing (0.722 → 0.700) and forum (0.752 → 0.740). The removed features had partly learned which sites were in the training set, so this is accepted as the cost of better generalisation.

  The 0.2.20 column was measured before the benchmark harness applied the provider's 2M-character input cap. Re-measured with the cap, 0.2.20 scores 0.8390 on WCXB dev; the other splits are unchanged. The selector margin stays 0.08: it is the only value tried (0, 0.04, 0.08, 0.12) under which 5-fold CV improves on the pre-selector baseline for all three development splits, and it was chosen on CV alone.
- **Threshold sensitivity check** (protocol rule 5, `benchmark/sweep-thresholds.sh`). Each hand-set candidate threshold (trailing prune: link density, article share, run share, uniform density band; rails: link density, minimum links; gate: article coverage) was rescored at ×0.75 and ×1.25 on WCXB dev and ScrapingHub. Every change stays within ±0.1pp, so none of them holds only at its chosen value. The two rail thresholds move nothing on these splits, which barely contain such rails. They rest on the CJK badcases alone.
- The scroll walk's cost on a ~30-viewport static article, measured in a real browser, went from 3.8s to 2.4s. Pages that do not scroll still pay nothing.

### Fixed

- **Deep capture now restores virtualized rows that have no DOM identity.** Until now the walk could restore only elements keyed by `id` or `data-block-id`. Lists whose rows carry no key (react-window, X-style timelines, where the framework key never reaches the DOM) came back as just the walk's final window. The walk now harvests such rows when the engine removes them: the `MutationObserver` record holds the detached row intact, plus the sibling nodes it sat between. The merge then splices each row back into its list, using no layout. Measured on the public react-window demo (1,000 unkeyed rows): rows 129–142 before, rows 1–155 in order with no duplicates after (stopped by the 20s budget). Details in the README's deep-capture section. New stats: `restored`, `rewound`.
- **Framework-generated ids are no longer treated as keys.** Ember's `emberN` and React `useId` values (`:r1:`, `«r1»`, `_r_1_`) change on every render, so they only ever stashed snapshots that could never match. Elements with these ids now take the unkeyed path.
- **A walk that restores nothing no longer hands the provider the bottom of the page.** The live read used to happen wherever the walk stopped. On a virtualizer the merge cannot rebuild (rows without text, canvas), that meant the last window replaced the opening screen the legacy capture returned. When the page reacted to scrolling, the walk now scrolls back to where it opened and waits for the page to settle before the read.
- A keyed wrapper around a restored list is never swapped for its one-window snapshot. The swap treats restored lists and their ancestors as containers.
- **The denoise input cap now applies on every path into the pipeline.** Previously only the live-render path capped the input. The unrenderable-loader fallback and the download/attachment refetch passed the whole body, and a multi-MB page could exhaust the heap. A cut input marks the result `truncated`.

### Added

- `docs/benchmark-protocol.md`: the rules for changing the denoise pipeline. It covers what each split may be used for (WCXB test and `fc` are held out), no site-specific rules, retraining both models when a feature changes, and sensitivity checks for hand-set thresholds.

## [0.2.20] - 2026-11-10

### Changed

- **Denoise is now "propose, then select" instead of one chain of global thresholds.** Each extraction heuristic proposes a candidate (`src/candidates.ts`): Readability with trailing-rail prune (`art`, the 0.2.18 path), unpruned (`artu`), and lenient (`artx`); the semantic main container (`main`); the whole document (`doc`, the old fallback) and a chrome-stripped one (`docc`: consent/cookie banners by name and wording, hidden subtrees, nav/menu/share/ad-named subtrees); the dominant repeated-record region (`rec`: product cards, list rows); noscript-unwrapped variants (`ns_art`/`ns_doc`, for Discourse-style server fallbacks); the Discourse `data-preloaded` post stream (`pre`); and a block-classifier pick (`blk`, `src/blocks.ts`: per-block content probability from gradient-boosted trees, kept blocks re-emitted in document order). A learned selector (`src/selector.ts`, gradient-boosted regression over page features such as generator meta, JSON-LD `@type`, `og:type`, URL shape, DOM statistics, plus candidate features such as size, link density, and block-level diffs against Readability) picks one candidate per page. The 0.2.18 choice is kept unless another candidate beats its estimate by 0.08, so a new heuristic can only add an option and cannot silently override the others. This retires the global-threshold conflicts of earlier releases: noscript unwrapping helped forums but hurt other pages when applied globally, and the 0.2.18 prune deleted link directories that were the content.
- `DenoiseResult` gains `strategy` (the chosen candidate kind). `mode` keeps its meaning: `document` for whole-document candidates, `article` otherwise.
- Models are generated files (`src/selector-model.ts`, `src/block-model.ts`) trained by the benchmark tooling: block classifier on WCXB dev + ScrapingHub, selector on WCXB dev + ScrapingHub + trafilatura, with cross-fitted block models so the selector never trains on in-fold block predictions. WCXB test was held out of both.
- Benchmark, stripped-markdown F1, v0.2.18 → v0.2.20: WCXB test (held out) 0.851 → 0.869; WCXB dev 0.792 → 0.840 (in-sample; 5-fold CV estimate 0.829); trafilatura 0.881 → 0.888; ScrapingHub 0.939 → 0.939. WCXB dev per type: forum 0.48 → 0.69, collection 0.59 → 0.69, listing 0.57 → 0.65, product 0.54 → 0.62, service 0.73 → 0.79, article 0.93 → 0.94. Pages under F1 0.3 dropped from 156 to 85, and empty outputs from 26 to 9. Known trade-offs: WCXB test article F1 −0.4pp (two pages); service precision −1.5pp and test forum precision −2.7pp, traded for larger recall gains.
- Denoise CPU cost is roughly 2.8× (WCXB dev p50 0.36s → 1.0s per page under 12-way parallelism), from multiple Readability passes and per-candidate sanitizing. That is small next to a browser fetch.

### Fixed

- Iterating element children no longer goes through jsdom's `HTMLCollection` proxy in the trailing-prune walk and the new candidate walks. On a 4,000-paragraph page, the proxy accounted for most of a 5s denoise.
- **Chinese and Japanese pages were measured as if each sentence were one word.** The selector and block features tokenized text with `[\p{L}\p{N}_]+`, so an unspaced Han or kana run counted as a single "word". A two-paragraph Chinese article then weighed about as much as a few headline links, and every ratio built on word counts was skewed: link density, size relative to Readability's pick, and block word counts. The skew pushed the selector toward whole-page candidates. Each Han or kana character now counts as one word. Text without CJK tokenizes exactly as before, so the models need no retraining and non-CJK outputs are unchanged.
- **Recommendation rails that outweigh a short article are now cut** (163.com `post_recommends` badcase: 28KB of recommended links around 170 characters of article). The 0.2.18 trailing prune keeps a rail that is more than 60% of Readability's pick, because that share guard is what protects docs indexes. Readability also strips the class names that would tell a rail from content. Rails are now recognised in the source DOM by name (`recommend*`, `related*`, Outbrain, Taboola) together with link density of at least 0.3 and at least 4 links. They are marked with a `data-*` attribute that Readability ignores, so it still picks the same container. They are then cut from the `art` candidate only when they follow prose inside the extraction. A "related-product" grid that opens a category page counts as content and is kept. The gate and the `artu` candidate still see the untouched extraction.
- Effect of the two fixes above, measured against the selector without them, stripped F1: WCXB dev 0.8398 → 0.8398, WCXB test 0.8691 → 0.8691, trafilatura 0.8881 → 0.8887, ScrapingHub 0.9392 → 0.9397. The per-cell regression gate passes with zero cells down. 11 of 3,179 pages changed output.
- On 30 live Chinese and Japanese pages (sina, sohu, ithome, cnblogs, people.com.cn, chinanews, ifeng, 163, qiita, zenn, sspai), 25 outputs were unchanged. Five pages that had returned the whole page or a recommendation-heavy page (14–44KB, 228–436 links) now return the article (0.2–2.3KB, 0–10 links).

## [0.2.19] - 2026-11-10

### Added

- **PDF links are extracted to Markdown instead of failing.** Previously any URL that served a PDF ended in `WEB_UNSUPPORTED_CONTENT_TYPE` — headless Chromium has no PDF viewer and hands the response to its download manager (`goto` rejects with `Download is starting`), and the download recovery refused undecodable types. The provider now routes PDFs to a dedicated extractor (`src/pdf.ts`) on every path one can arrive by: an inline `application/pdf` (download in headless Chromium; committed into the viewer in a headed or CDP-attached Chrome, verified against full Chrome's new-headless mode, whose `response.body()` returns the 536-byte viewer wrapper rather than the PDF), a `Content-Disposition: attachment` download, and an opaque `application/octet-stream` (or a `.pdf` path or filename) whose bytes sniff as `%PDF-`. The bytes come from the navigation body when it is the PDF, else from a refetch through the page's API request context, which rides the browser context's cookie jar, so gated PDFs behind a login work in CDP profile mode (covered by a real-browser test). Extraction uses pdf.js 6 through `unpdf`'s serverless build, imported lazily so plugin start never pays for it, and reads positioned text runs plus real font names (operator list + `fontExtraProperties`) per page. A pure, unit-tested layout pass then rebuilds the document: lines grouped by baseline; rotated runs (arXiv's side stamp) dropped; running headers/footers (margin text repeated across pages) and page numbers (`Page 3 of 9`, `— 12 —`, `·１·`, including OCR'd `一 2 一`) removed; body size and line pitch measured. Headings come from the outline (with a title-root offset), section numbering (`3.1`, `A.2`, `第二章`, `一、`, `（一）`), ranked larger type (the largest first-page type is the `#` title, else the metadata title when plausible), and standalone bold lines (one level below the current section; run-in bold leads stay inline `**bold**`). Paragraphs split on gaps, first-line indents, and short sentence-final lines, and continue across columns and pages while a sentence is unfinished, with de-hyphenation (`-`, U+2010, soft hyphen) checked against the document's own vocabulary and CJK-aware joining. Bullets (including Symbol-font private-use glyphs) and numbered items become lists, monospace-named fonts become fenced code with measured indentation (unless the whole document is monospace), and multi-cell rows whose column starts line up become GFM tables (justified prose and form lines are rejected). Table-of-contents entries split per entry, CJK letter-spacing is collapsed, and Kangxi / C-simplified radical look-alikes that some producers' ToUnicode maps emit (Chromium printing Noto CJK: `⽂`, `⻓`) are normalized to the real ideographs. Each page is marked `<!-- page N -->`. Measured on real links: arXiv (Attention, BERT: titles, numbered section tree, inline bold, result tables), the IRS W-4 form, RFC 9110 (title + abstract; truncated at the 100k body cap), an OCR'd scan of the 2017 Chinese government work report (`一、` headings, paragraphs joined across pages), and a 266-page NPC gazette (outline-driven chapters, TOC entries, `第X条` articles; stopped at the character cap).
- **PDF error codes**: `WEB_PDF_NO_TEXT` (no text layer — a scan; OCR is not supported), `WEB_PDF_ENCRYPTED`, `WEB_PDF_INVALID` (bytes that claim or sniff as PDF but do not parse), and `WEB_PDF_TOO_LARGE` (over 50MB, checked against `Content-Length` before downloading). Reading stops after 500 pages, 100k collected characters, or the fetch deadline (minus a 1.5s finish reserve); the result is flagged `truncated` and ends with a note naming the last page read.
- `scripts/make-pdf-fixtures.mjs` regenerates the committed fixtures (`tests/fixtures/pdf/`: a Chromium-printed 4-page handbook with outline, numbered headings, hyphenation, lists, code, table, Chinese paragraphs, and a running header/footer; an image-only scan; a minimal encrypted PDF; a broken one). New `tests/pdf.spec.ts` (heuristics over synthetic runs, one rule per case, plus the pdf.js path over the fixtures), provider tests for every routing path, and real-browser integration tests (inline, attachment, sniffed octet-stream, non-PDF binary, scan, and a cookie-gated PDF over CDP).

### Changed

- A non-PDF binary download (`application/zip`, …) still fails with `WEB_UNSUPPORTED_CONTENT_TYPE`; an `application/octet-stream` download is now refetched once to sniff for PDF bytes before failing.
- New runtime dependency: `unpdf` (^2.1.0, bundles pdf.js 6.4).

## [0.2.17] - 2026-11-09

### Added

- **Deep capture for viewport-virtualized feeds and app-shell documents** (badcases: `https://linux.do/t/topic/3143069` → main post intact, all 20 replies reduced to bare "由 X 发布" screen-reader headings; `https://linux.do/t/topic/3143588` → replies past the first ~6 empty; a Feishu wiki page `bocha-ai.feishu.cn/wiki/UkoowVVSWiWybgkJT0EcW7Tqno5` → 7 blocks / 892 chars of a ~190-block document). Feed-shaped pages (Discourse topic streams, comment threads, timelines) render only the items near the scroll position and keep every other item as a height-only placeholder that carries its id but none of its content; app-shell editors (Feishu and kin) go further — html/body are locked at one viewport so the document scrolls inside an inner container, blocks are keyed by `data-block-id` with no id, and off-window blocks are *removed* behind one anonymous height spacer. A resting single-instant capture therefore returned the skeleton or the first screen, and the denoise coverage gate could not notice (the page's own visible text is the same windowed fragment as the extraction); one jump to the bottom does not help either, because the render window *moves* and later chunks only load when a load-more sentinel fires. The fetch now runs one bounded in-page scroll walk (`src/autoscroll.ts`) between the settle and serialization: (1) it resolves the walk target — the window when the document scrolls, else the page's dominant `overflow-y: auto|scroll` container (gated at half a viewport so dropdown-sized scrollers never trigger it); (2) it stashes every keyed element (id, else namespaced `data-block-id`) as a detached clone, keeping the richest sighting per key plus its nearest keyed siblings, with entries size-capped at ~64KB so page-wrapping containers cannot exhaust the stash (measured on linux.do: six nested wrappers alone ate 1.9MB of a 2MB budget before any post); (3) it walks down in 0.7-viewport steps of 300ms smooth motion plus a 300ms settle (instant steps starved Discourse's debounced uncloak), and holds at the bottom through a 2.5s patience window that any height growth restarts; (4) it merges into a structural clone (`document.cloneNode(true)`) — swapping each degraded keyed element for its snapshot (containers are assembled from their restored descendants instead of their own partial-window snapshot) and, on container walks, splicing removed blocks back beside their recorded keyed siblings, so order holds even for an anchored mid-document open — then strips scripting elements from the clone (shared `src/strip.ts`) and serializes it. The live page is never rewritten, and the clone has no browsing context, so no script, custom-element upgrade, or frame load runs during the merge, and no serialize/re-parse round trip can let a runtime-rewritten data script corrupt it (the 0.2.15 hazard). Scroll-inert pages — most of the web — are detected by a `MutationObserver`: after two careful steps with no element added or removed, the rest is probed with one jump to the bottom, and any reaction after that jump rewinds and finishes carefully, so correctness never rests on the guess (a ~30-viewport static article drops from exhausting the budget to ~4.5s). A walk that restored nothing hands back no HTML and the existing live read proceeds unchanged; any failure (no `evaluate`, a rejected evaluation) silently degrades to the legacy capture — the walk can only add content, never fail a fetch. Measured on the live badcases: the 51-reply linux.do topic walks fully within one budget with every post rehydrated and zero cloaked placeholders left; meta.discourse.org (46 replies) goes from 25 skeleton headings and a truncated tail to reaching the newest reply; the Feishu page walks its inner container in 11.5s (15 steps, 38 removed blocks spliced back, 7 → 191 blocks, 892 → 3457 markdown chars, the deep tail's JSON examples included). Known limitation: Feishu table cells sit behind a second, in-block virtualization the walk does not chase — headers and rows are restored, very large payload cells may stay empty. Regression coverage: the composed in-page expression runs in jsdom against scripted virtualizers, and real-browser integration fixtures (Discourse-shape windowed stream with load-more chunks, app-shell locked body with `data-block-id`-only blocks and lazy chunks, a coarse virtualizer exercising the rewind path, an anchored app-shell open, the data-script rewrite, a static article's walk cost, and a plain-article control) prove the baseline returns the skeleton while the walk returns every item exactly once, on both the denoised and raw-HTML paths.

- **`scrollBudgetMs` setting** (default `20000`, range 0–30000, live-editable in the settings card, en/zh-CN locales and both READMEs). It bounds the deep-capture walk together with the remaining fetch deadline minus a decode reserve; `0` disables the walk and restores the pre-0.2.16 single-instant capture.

### Changed

- **Fetches of scroll-reactive pages can take longer by default.** The walk is on out of the box, so a page that genuinely virtualizes or lazy-loads on scroll now spends up to `scrollBudgetMs` (20s) of the 45s per-fetch deadline walking it; scroll-inert pages exit through the fast path in a few seconds, and documents that do not scroll at all skip the walk entirely. Set `scrollBudgetMs: 0` to return to the previous timing.

## [0.2.16] - 2026-11-09

### Fixed

- **A Turnstile widget embedded in a normal page is no longer mistaken for a challenge interstitial** (badcase: `https://linux.do/t/topic/3143588` → `WEB_FETCH_CHALLENGE` "(last status 200)" after 37s, surfacing to the agent as a bare 30s `web_fetch` timeout — the exact symptom class as 0.2.12, through a third false-positive path that fix could not see). linux.do is a Discourse forum behind Cloudflare whose Turnstile plugin mounts a *genuine* Turnstile widget — container `id="cf-chl-widget-…"` and all — into every normal topic page it serves at HTTP 200 through a logged-in profile; the response carries `server: cloudflare`/`cf-ray`, so the suspicion gate opens on every page, the `id="cf-chl-widget-` marker read the widget as interstitial proof, and the bounded wait could never confirm a clear (the DOM probe's `[id^="cf-chl-widget-"]` matches the real page *forever*, even after a genuine challenge has cleared into it) — two 15s attempts against a 4–7s page load, past the `web_fetch` tool's 30s budget, so the agent saw a generic timeout rather than either the article or the challenge error. The failure is RACY in deployed builds because Discourse mounts the widget lazily: a fetch whose content check runs before the widget mounts squeaks through in ~28s (itself a near-miss against the 30s budget), one that runs after dies at 37s. The fix is a signal-tiering rule, not a new heuristic: a Turnstile widget id is minted by the same Turnstile runtime whether it renders inside an interstitial or inside a site's own UI (login modals, contact forms, Discourse's per-topic widget), so it proves only "this page embeds Turnstile" and is dropped from `CHALLENGE_HTML_MARKERS` and from the `CHALLENGE_DOM_PROBE` selector — while every independent interstitial signal stays sufficient on its own: the documented `cf-mitigated: challenge` header, the 403/503 + `server: cloudflare` response shape, the localized `<title>` family, the positively-identified `/orchestrate/` runtime script, `window._cf_chl_opt`, the `#challenge-*` scaffolding, and the Crawlee footer combo. No real interstitial loses detection: each one carries its localized title and challenge bootstrap beyond any widget, and a widget *next to* any independent signal still classifies (covered by tests). This also un-breaks the wait path for widget-embedding sites whose challenge really did clear — the probe now reports the clear instead of burning the window against the real page. Regression coverage: the linux.do shape as a pure-fixture unit test (real title, embedded widget, JSD instrumentation → `none`; widget + each independent signal → `challenge`), the probe mirror (real title + widget selector → not challenged), and a real-browser integration test serving the exact shape at 200 behind `server: cloudflare` with the full feature stack on — verified to fail without the fix (the old marker enters the wait) and to fetch clean in one navigation with it; the existing A/B suite (reload-clear, SPA-clear, chained, never-clearing, fast-clear — all on a widget-free interstitial fixture, i.e. real-challenge detection never depended on the widget) stays green. Verified end-to-end at the provider level against the real site and the user's real remote-Chrome config (CDP profile mode, `fetchProvider: playwright`): the pre-fix build reproduces both outcomes (37s `WEB_FETCH_CHALLENGE` "last status 200", and a racy 27.8s near-miss success), while the fixed build returns the real topic markdown 3/3 times in 8.0–11.5s; linux.do's real 403 interstitial against a local headless backend is still detected, waited across both attempts, and surfaced as a bounded `WEB_FETCH_CHALLENGE` (last status 403) when the browser cannot clear it naturally.

- **List-shaped pages no longer collapse into a noise fragment** (badcase: `https://www.163.com/` → a 162-character markdown body consisting of the footer licensing notice "粤B2-20090191-18 … 主办单位：广州网易计算机系统有限公司" — 0% of the page's 320 news headlines, 1.7% of its visible text). Readability is an article extractor: it scores text mass, penalizes list tags (`UL/OL/LI/DD/DT` start at −3), skips every text run under 25 characters (a headline's native size), and multiplies each candidate's score by `(1 − linkDensity)` — on a portal page, where the content *is* the links, every news column's density is 0.82–0.93 and its score collapses to ~zero, so some sparse low-link block wins by default (measured on the badcase: `<div class="subfoot_zbdw">`, 96 characters, score 7.08 vs dozens-to-hundreds for a real article's top candidate). Readability's own 500-character quality check cannot fail such a parse because its retry loop strips flags four times and then *returns the longest of its bad attempts as success* — so the plugin's only gate, `article.content !== ''`, always passed and the whole-document fallback was unreachable. The pipeline now wraps the acceptance in a coverage gate (`articleCoversPage` in `src/markdown.ts`): an extraction is trusted only when it carries at least 250 non-whitespace characters AND covers at least 10% of the page's visible text, measured by a walk that skips the very subtrees DOMPurify's `KEEP_CONTENT: false` deletes (`FORBID_TAGS` + `script`/`style`), so the denominator is what the document fallback could actually return rather than text already destined for deletion; pages with under 1,000 visible characters stay ungated, keeping sparse-page behavior byte-identical. A distrusted extraction flows into the pre-existing sanitized whole-document path — measured on the badcase family: 163.com homepage 0% → 98% headline recall (59.5KB body), sina.com.cn 402 garbage characters → 100% recall, while article pages (163 news articles, MDN) remain in article mode with unchanged output, and sohu.com — whose visible text survives inside Readability's own pick at 10.5% coverage — is unchanged by design. The measured separation between portal pages (coverage 0.01–0.03) and article pages (0.28–0.45) leaves the 10% threshold in an empty band with margin on both sides; the worst case the gate can cause is a fallback to the already-sanitized whole document, trading precision for recall — for an LLM-facing fetch the 0%-recall failure it fixes is strictly worse.

## [0.2.15] - 2026-11-09

### Fixed

- **A runtime-rewritten data script no longer corrupts the fetched article** (badcase: `https://techcommunity.microsoft.com/blog/microsoft-security-blog/remote-desktop-protocol-rdp-10-avch-264-improvements-in-windows-10-and-windows-s/249588` → HTTP 200 carrying CSS rules and `CachedAsset` i18n strings instead of the RDP 10 AVC/H.264 body). Root cause is a serialization round-trip hazard, verified against a real browser: the page's runtime JS writes its whole Apollo cache back into `script#__NEXT_DATA__.textContent` via `JSON.stringify` *without re-escaping*, planting a literal `</script>` inside script text (the wire response escapes `<` 712 times as `\u003c`; the rewrite un-escapes them), and `page.content()` serializes script text verbatim — so the HTML string the denoise pipeline re-parses with jsdom ends that script at the *first* embedded end tag and parses the remaining ~270KB of JSON *as markup*. The phantom elements that survive (unknown tags like `<id>`, anchors full of CSS and i18n text) are exactly what Readability's scorer reads as article mass — measured 126 points vs the real body's 45 — so the extraction returns the cache payload while the (still present) article loses; no string-level patch can disambiguate that serialization after the fact, because only the browser's own parse holds the document's true structure. The fix strips non-content scripting subtrees inside the live page (`page.evaluate`, best-effort, skipped gracefully when a backend exposes no `evaluate`) right before `page.content()` — ordinary `script` and `template` only, with two deliberate carve-outs that keep the change output-neutral everywhere else: `script[type="application/ld+json"]` is defused rather than deleted (`</` → `<\/`, still valid JSON, so Readability's metadata pass keeps yielding the site-suffix-free article title — deleting it regressed Wikipedia's title to "… - Wikipedia" in an earlier iteration), and `noscript` is kept entirely because Readability's `_unwrapNoscriptImages` salvages lazy-load images out of it. Neutrality was audited both by code path (Readability removes script/noscript before extraction AND scoring, DOMPurify's allowlist drops script, and the tool layer's renderer removes SCRIPT/NOSCRIPT/TEMPLATE wholesale on the raw path, where JSON-LD was never surfaced either) and empirically: differential A/B over a real-page corpus (Wikipedia, MDN, Hacker News, example.com, the badcase page's wire HTML, plus JSON-LD-title, noscript-image, inline-data-island, and template edge cases) is **byte-identical on every page** — the first iteration's two real regressions (JSON-LD title, noscript images) were caught by exactly this differential and carved out. On the badcase the fetch now returns the real article (H.264 ×25, zero cache strings, on the captured fixtures), the `denoise: off` path hands the tool layer a serialization-safe document, and the pipeline input shrinks ~70%. Regression coverage: the full captured document pair (corrupted/stripped, `tests/fixtures/techcommunity-*.html`) drives provider tests asserting the article survives and the cache payload is gone (plus the no-`evaluate` degradation), and a real-browser integration test serves a page whose own JS performs the un-escaped rewrite while carrying a JSON-LD script and a noscript lazy-load image — verified to fail without the strip (the soup leaks into the result), with the carve-outs removed (the title falls back to the site-suffix form), and to pass with the fix.

### Fixed

- `web fetch aborted while waiting for a free browser slot` no longer surfaces as the common failure under parallel `web_fetch` bursts: the CDP default alone covers 50 concurrent tabs, and a queued fetch that gets no slot within 20s fails fast with `WEB_FETCH_TIMEOUT` plus a retry/`maxConcurrency` hint instead of hanging until an abort mislabels it.
- Queue-wait errors translate through the standard taxonomy: the provider's own deadline expiring while queued reports `WEB_FETCH_TIMEOUT`, and a caller cancelling a queued fetch keeps the precise slot message under `WEB_ABORTED`.
- Cleanup hardening: context/browser closes in the fetch teardown are grace-bounded (2s), so a wedged Playwright close can no longer pin a concurrency slot forever (which previously made every later fetch die on the queue), and a queued fetch that fails to acquire never releases a phantom slot.

### Added

- `CdpConnectionPool` (exported): the shared-connection core — one connect under concurrent acquires, per-fetch context leases, liveness probes (`isConnected` + `disconnected`), single reconnect-and-retry, generation-guarded abandonment of connects made stale by an endpoint change or dispose.
- `effectiveMaxConcurrency(config)` and the `DEFAULT_MAX_CONCURRENCY_LOCAL` / `DEFAULT_MAX_CONCURRENCY_CDP` / `MAX_CONCURRENCY_CEILING` constants.
- Provider `dispose()` plus a `ctx.effect` teardown hook in the plugin entry that drops the shared CDP connection on unload.
- Tests: the CDP pool (8 cases), provider-level CDP behavior (one connection, tabs closed per fetch, 50-way tab burst, dead endpoint), queue cases, and a real-Chromium CDP integration smoke (debugging port, denoise fetch, 12-tab concurrent burst) that self-skips without a browser.
